# Data Field Specification — BLW KTU First Timer Card & Attendance Sheet

**Purpose:** This document maps the exact fields from the physical BLW KTU (Christ Embassy Campus Ministry) paper forms to the app's data model, so the frontend forms and backend schema (Room locally, later Supabase) stay in sync with what the church actually uses.

**Source:** Physical "First Timer Card" and "Attendance Sheet" currently in use.

---

## 1. First Timer Card — Fields

| Field (as on card) | Maps to | Type | Required | Notes |
|---|---|---|---|---|
| Date | `attendance.service_date` | date | Yes | Auto-filled from session, not re-entered |
| Service Type | `attendance.service_type` | enum | Yes | See §3 for the fixed set used on the attendance sheet (Sun/Wed/Fri/Cell) |
| Surname | `member.surname` | string | Yes | Split from a single "name" field into surname + first name to match the card exactly |
| First Name | `member.first_name` | string | Yes | |
| Course of Study | `member.course_of_study` | string | No | Campus-ministry specific — not in original design doc, added here |
| Level | `member.level` | string | No | e.g. "300" — matches KTU's academic level system |
| Hall/Hostel & RM No | `member.hall_hostel`, `member.room_no` | string, string | No | Two fields on the card ("Hall/hostel" and "RM No") |
| Date of Birth | `member.date_of_birth` | date | No | |
| Email | `member.email` | string | No | |
| Phone No(s) | `member.phone` | string | Yes | Card allows multiple numbers — store as one string field, comma-separated if more than one |
| Who invited you? | `first_timer.invited_by` | string | No | Free text (name of inviter) |
| Are you born again? | `first_timer.is_born_again` | boolean/enum | No | Yes/No |
| Do you speak in tongues? | `first_timer.speaks_in_tongues` | boolean/enum | No | Yes/No |
| Would you like to be a member of BLW? | `first_timer.wants_membership` | boolean/enum | No | Yes/No |
| Prayer request or Testimony | `first_timer.prayer_request` | text | No | Multi-line free text |
| Department interest (checkboxes) | `first_timer_department` (join table) | multi-select | No | Ushering / Choir / Technical / Creative Art / Media & New Media / Innovations — a person can select more than one |

## 2. Attendance Sheet — Fields

| Field (as on sheet) | Maps to | Type | Required | Notes |
|---|---|---|---|---|
| Date | `attendance.service_date` | date | Yes | Header field, applies to the whole sheet |
| Service Day (Sun/Wed/Fri/Cell) | `attendance.service_type` | enum | Yes | Fixed set — see §3 |
| S/N | — | — | — | Row number, not stored (auto-generated by list order) |
| Full Name | `member.surname` + `member.first_name` | string | Yes | Sheet uses one combined "Full Name" column — app keeps surname/first name split (per Card, §1) and displays them combined |
| Contact | `member.phone` | string | Yes | |
| Email | `member.email` | string | No | |
| Hall/Hostel/RM | `member.hall_hostel`, `member.room_no` | string, string | No | Same fields as the First Timer Card |
| Course | `member.course_of_study` | string | No | Same field as the First Timer Card |
| Level | `member.level` | string | No | Same field as the First Timer Card |
| B/Day (Birthday) | `member.date_of_birth` | date | No | Same field as the First Timer Card's Date of Birth |

**Key implication:** Every field on the Attendance Sheet already exists on the Member record from the First Timer Card. This confirms the original design — a **returning member** should never re-enter this data; they only need to be found and marked present. Only a **first-timer** fills the full form.

---

## 3. Service Type — Updated Enum

The physical attendance sheet uses a fixed, simpler set than originally drafted. Update the `service_type` enum to match exactly what's on the ground:

```
SUN   → Sunday Service
WED   → Wednesday Service
FRI   → Friday Service
CELL  → Cell Meeting
```

This replaces the earlier draft list (Sunday 1st/2nd/3rd Service, Midweek, Special Program) with the actual set in use. If Communion Services or special programs need separate tracking later, they can be added as additional enum values without breaking existing data.

## 4. Consolidated Data Model (updates existing entities)

### `Member` (Room entity — updates original `members` table)

```java
@Entity(tableName = "members")
public class Member {
    @PrimaryKey(autoGenerate = true)
    public long id;

    public String surname;
    public String firstName;
    public String phone;
    public String email;              // optional
    public String courseOfStudy;      // optional
    public String level;              // optional
    public String hallHostel;         // optional
    public String roomNo;             // optional
    public String dateOfBirth;        // optional, ISO date string

    public String joinDate;           // set on first registration
    public boolean isFirstTimerOrigin;
    public String cellZone;           // optional, future follow-up use
}
```

### `FirstTimer` (Room entity — updates original `first_timers` table)

```java
@Entity(
    tableName = "first_timers",
    foreignKeys = @ForeignKey(
        entity = Member.class,
        parentColumns = "id",
        childColumns = "memberId"
    )
)
public class FirstTimer {
    @PrimaryKey(autoGenerate = true)
    public long id;

    public long memberId;             // FK -> Member

    public String invitedBy;          // optional, free text
    public Boolean isBornAgain;       // nullable
    public Boolean speaksInTongues;   // nullable
    public Boolean wantsMembership;   // nullable
    public String prayerRequest;      // optional, multi-line

    public String followUpStatus;     // New / Contacted / Attended again / Integrated
    public String assignedTo;         // optional, future use
}
```

### `FirstTimerDepartment` (new join table for multi-select checkboxes)

```java
@Entity(
    tableName = "first_timer_departments",
    foreignKeys = @ForeignKey(
        entity = FirstTimer.class,
        parentColumns = "id",
        childColumns = "firstTimerId"
    )
)
public class FirstTimerDepartment {
    @PrimaryKey(autoGenerate = true)
    public long id;

    public long firstTimerId;         // FK -> FirstTimer
    public String department;         // Ushering / Choir / Technical / Creative Art / Media & New Media / Innovations
}
```

### `Attendance` (Room entity — unchanged from original design)

```java
@Entity(tableName = "attendance")
public class Attendance {
    @PrimaryKey(autoGenerate = true)
    public long id;

    public long memberId;             // FK -> Member
    public String serviceDate;
    public String serviceType;        // SUN / WED / FRI / CELL
    public long registeredBy;         // FK -> Usher
    public long timestamp;
    public boolean synced;            // used from Phase 8 onward
}
```

## 5. Frontend Form Implications

- **First Timer form** should be built as a single scrollable form matching §1 field-for-field, including the department checkboxes as a multi-select group (not a dropdown, to match the physical card's UX)
- **Register Member (search) flow** doesn't need any of these fields re-entered — it only needs enough to search (name or phone) and confirm a match, since everything else already lives on the `Member` record from their first-timer registration
- **Service type selector** (Phase 3 of the roadmap) should use the 4-option set from §3, not the original longer list

## 6. Backend/Sync Implications (Phase 8, Supabase)

- Mirror all four tables (`members`, `first_timers`, `first_timer_departments`, `attendance`) in Postgres with matching foreign keys
- `first_timer_departments` becomes a proper many-to-many-style table in Postgres — trivial to query for "how many first-timers are interested in Media & New Media this term," which is a natural report a pastor would want
